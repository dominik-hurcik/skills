# Frontend design

Work like an experienced design director who also ships production code. Form a clear point of view, then build it carefully.

## Ground rules

- Finish the job. Deliver complete work. The only gaps allowed are assets the user must supply, and say which ones.
- The brief wins. Keep pinned fonts, palettes, eras, and materials, even when they clash with the defaults in this skill.
- Refinement keeps what exists. Redesign replaces the look but keeps the product's facts, copy, and behavior. Ask before you change factual copy or add claims.
- Check the rendered result, not only the code. View it at the sizes users will see.
- Use real content. Label demo data as demo data. Do not invent statistics, testimonials, or logos.
- Keep symbols tied to militarism, supremacy, or hate movements out of decoration. Content that documents them as fact stays.

## Modes

Pick the mode from the surface, not the product. A product's landing page is Persuade. The same product's docs are Read.

| Mode | The visitor | Typical surfaces | Ambition shows as |
| --- | --- | --- | --- |
| Persuade | Decides and acts | Landing pages, campaigns, pricing | Bold, distinct work with a point of view |
| Operate | Completes a task | App UI, dashboards, editors, settings | Precision, consistency, familiar patterns |
| Read | Understands something | Docs, articles, guides, changelogs | Clear structure and a comfortable reading experience |
| Experience | Looks at the work | Portfolios, galleries, showcases | The work leads and the interface steps back |

On Operate and Read surfaces, use patterns the visitor already knows. On Persuade and Experience surfaces, commit to a point of view.

## Workflow

1. **Read the context.** Look for design notes (`PRODUCT.md`, `DESIGN.md`) and the existing tokens, components, and styles. Use what exists. Do not invent a system the project lacks.
2. **Choose the job.** Find the matching reference in the table below. For a new surface or a new visual identity, start with [new-work.md](references/new-work.md).
3. **Read the craft floor** before any UI edit, even a small one: [craft-floor.md](references/craft-floor.md).
4. **Build or change the UI.** Keep the existing identity unless the job is a redesign.
5. **Verify.** Render the result at desktop and mobile widths. Run the craft-floor checks in one batch, and fix everything one look reveals before you look again.
6. **Polish.** For shipping work, do the final pass in [polish.md](references/polish.md).

If you cannot run the app or take screenshots, read the code closely. Say what you could not check and list what the user should look at.
